## Node.js 24 to 26

- **Lifecycle:** Node 26.13.0 is the first LTS release, codenamed Lithium, with updates through the end of April 2029. Node 24 remains LTS; its latest listed release is 24.22.2. Node 25 is end-of-life and should not be selected as the migration target. Node 26 follows the old even-numbered schedule; the annual schedule starts with Node 27 ([26.13.0 release](https://nodejs.org/en/blog/release/v26.13.0), [release status](https://nodejs.org/en/about/previous-releases), [schedule announcement](https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule)).
- **Bootstrap:** Node 25 stopped distributing Corepack, so Node 26 installs must not assume it comes with Node. Install pnpm by a supported independent method, or separately install and enable Corepack if that is the chosen workflow ([Node 25.0.0](https://nodejs.org/en/blog/release/v25.0.0), [pnpm installation](https://pnpm.io/installation)). Update `.nvmrc`, `package.json`'s Node and pnpm `engines`, `packageManager`, `README.md`, and any CI/setup references together. The present `.npmrc` sets `engine-strict=true`; the present Node range `>=24 <25` rejects Node 26. Decide whether the project intends Node 26 only, for example `>=26 <27`, or retains tested Node 24 support; do not silently claim support for versions not tested. If 26-only is intended, review `tsdown.config.mjs`'s `target: "node24"` as well; retaining the lower output target is not itself a runtime error.
- **Runtime differences:** Node 26 removes `http.Server.prototype.writeHeader()` and legacy `_stream_*` modules; `module.register()` is runtime-deprecated; `--experimental-transform-types` was removed; V8 and bundled Undici were upgraded, and the native module ABI changed to 147. Check direct and transitive tooling warnings and reinstall platform-specific native packages rather than reusing a Node 24 `node_modules` tree. On Linux, official Node 25+ binaries link against `libatomic`, which may need separate installation ([Node 26.0.0](https://nodejs.org/en/blog/release/v26.0.0), [Node 26.13.0](https://nodejs.org/en/blog/release/v26.13.0)).
- **TypeScript execution:** Node's built-in TypeScript stripping is stable, but performs no type checking, does not read `tsconfig.json`, and only handles erasable syntax. The current scripts use `tsx` and imports such as `./process.js`; replacing `tsx` with `node` is not implied by this upgrade and would require separate compatibility testing ([Node TypeScript docs](https://nodejs.org/api/typescript.html)).

## pnpm 12: install, lockfile, and supply-chain behavior

- **Pin and regenerate coherently.** Set `packageManager` to `pnpm@12.16.1` and update its engine range before regenerating the lockfile. pnpm 12 can read existing frozen lockfiles, but a dependency re-resolution may re-key cyclic peer variants. In addition, the new pinned pnpm version must be reflected in the bootstrap lockfile: a frozen install fails when that record is absent or outdated. Run a non-frozen install intentionally, inspect the entire diff, then test `pnpm install --frozen-lockfile` in a clean environment. Do not expect `pnpm install --frozen-lockfile false` to work; use `--no-frozen-lockfile` ([pnpm 12.0.0](https://github.com/pnpm/pnpm/releases/tag/v12.0.0), [lockfile documentation](https://pnpm.io/lockfile)).
- **Important scanner risk:** With a pnpm 12 `packageManager` pin, the generated `pnpm-lock.yaml` can have a first YAML document for the bootstrap pnpm/config dependencies and a second for the project's dependency graph; both can say `lockfileVersion: '9.0'`. A scanner reading only the first document may report no project dependencies or vulnerabilities. Verify dependency graph, SBOM, audit and update tooling against a two-document fixture; graph tools should read the last document, while inventory/security tools need all documents. `pnpm audit` supports both shapes. Do not disable pin enforcement merely to work around an unverified scanner without a deliberate tradeoff ([pnpm lockfile documentation](https://pnpm.io/lockfile)).
- **Strict settings and engines:** pnpm 12 rejects unrecognized workspace settings when the running version satisfies the project pin. The current `updateConfig.ignoreDependencies` is a deprecated but still supported alias of `update.ignoreDeps`; if renaming it, retain the deliberate `@types/node` exclusion unless its removal is intended. Under `engineStrict`, pnpm 12 fails on an incompatible package reached through a regular dependency edge even if the subtree descends from an optional dependency, where pnpm 11 could warn. Preserve `allowBuilds.esbuild: true` and review any additional blocked build scripts rather than approving all scripts blindly ([pnpm 12 release](https://github.com/pnpm/pnpm/releases/tag/v12.0.0), [resolution settings](https://pnpm.io/settings/dependency-resolution#update), [build settings](https://pnpm.io/settings/build)).
- **Release-age and trust checks:** The 1,440-minute built-in `minimumReleaseAge` is non-strict if not explicitly configured. When configured explicitly, `minimumReleaseAgeStrict` defaults to true: if no eligible version matches, resolution fails instead of falling back. pnpm can re-verify the loaded lockfile's age/trust policy even on frozen installs; `trustLockfile` defaults to false. `trustPolicy` defaults to off, so do not claim provenance downgrade checks are enabled. Missing registry `time` metadata is skipped by default; organizations that require fail-closed behavior should explicitly decide whether to change that setting. Do not use `trustLockfile` or broad age exclusions just to make CI pass. Review the existing version-specific `tsdown@0.22.14` and `verkit@0.3.0` age exclusions after re-resolution and remove only those shown to be unnecessary ([pnpm 12.3.0](https://github.com/pnpm/pnpm/releases/tag/v12.3.0), [resolution settings](https://pnpm.io/settings/dependency-resolution), [supply-chain guidance](https://pnpm.io/supply-chain-security)).
- **Fresh releases and CI:** If a locally generated lockfile includes an immature version under an exception or weaker policy, frozen CI with a stronger policy can reject it. Check direct and transitive versions, registry timestamps and environment-specific settings; either wait for the cutoff or explicitly approve a narrowly scoped exception. Never assume a frozen lockfile skips policy verification ([pnpm settings](https://pnpm.io/settings/dependency-resolution#trustlockfile)).
- **Other 12.x changes:** pnpm 12 canonicalizes known-host Git dependencies to HTTPS; private Git repositories that rely on SSH need machine-level Git URL rewriting. `pnpm setup`, `self-update`, and mutating global commands under `sudo` now fail. pnpm 12.16 changes global installations to use the global virtual store by default; store/linker conflicts now produce explicit errors on global commands. These are relevant to portability, even though no direct Git dependency is currently declared ([12.0.0](https://github.com/pnpm/pnpm/releases/tag/v12.0.0), [12.16.0](https://github.com/pnpm/pnpm/releases/tag/v12.16.0)).

## Global CLI installation

`scripts/install-global.ts` builds the CLI, queries `pnpm bin --global`, and executes `pnpm --config.minimum-release-age=0 add --global <checkout>` from the OS temporary directory with `CI=true`. pnpm 12.3 fixed `pnpm add <local directory>`, which supports retaining this approach on 12.16.1, but the exact installed and packed behavior has **not** been tested here ([pnpm 12.3.0](https://github.com/pnpm/pnpm/releases/tag/v12.3.0)).

The existing command explicitly disables the release-age check for the entire global add, including its transitive resolution; it is not merely an exception for the local checkout. It runs outside the project root, so do not assume project workspace policy or its exceptions apply. Decide whether that bypass is acceptable and document it; avoiding it or reducing its scope may require a deliberate installer change and a fresh-install test. This flag does not by itself establish that all other security policies are bypassed ([pnpm resolution settings](https://pnpm.io/settings/dependency-resolution)).

Validate in an isolated user environment without `sudo`: `pnpm setup`/`PNPM_HOME` and PATH, `pnpm bin --global`, local checkout installation, executable discovery from another directory, actual PDF generation, and uninstall/upgrade behavior. This mutates a user's global installation, so use a disposable profile or obtain approval. pnpm's context-aware shims can switch pinned Node or package-manager versions by project; ordinary package bins do not automatically become context-aware. pnpm 12.3 uses native executables for its context-aware Windows shims, not necessarily every ordinary CLI shim. Test Windows instead of assuming the script's reported `.cmd` path applies to all shim types ([pnpm 12.0.0](https://github.com/pnpm/pnpm/releases/tag/v12.0.0), [pnpm 12.3.0](https://github.com/pnpm/pnpm/releases/tag/v12.3.0)).

## Direct dependency migration details

- **jsdom 30 and DOMPurify:** jsdom 30 raises its Node requirement to `^22.22.2 || ^24.15.0 || >=26.0.0`; its release notes also describe CSS serialization and computed-style changes. `src/converter.ts` uses jsdom for both alert rewriting and DOMPurify sanitization, so update `@types/jsdom` to 30.0.0 and verify HTML/SVG sanitization, alert transformation, malformed markup and snapshots, not just startup. DOMPurify 3.4.17 hardens namespace, literal-text and attribute handling, among other fixes; keep security regression tests and evaluate changed output ([jsdom 30.0.0](https://github.com/jsdom/jsdom/releases/tag/v30.0.0), [jsdom 30.1.3](https://github.com/jsdom/jsdom/releases/tag/v30.1.3), [DOMPurify 3.4.17](https://github.com/cure53/DOMPurify/releases/tag/3.4.17)).
- **Playwright:** The 1.64 release lists Chromium 156 and changes several test-runner and visibility behaviors; 1.63 drops Ubuntu 20.04 support and 1.62 drops Debian 11. This project launches Chromium directly and generates PDFs, not Playwright Test. Re-run `pnpm exec playwright install chromium` after updating, then check PDF layout, fonts, images, Mermaid rendering and browser availability in CI and from the globally installed CLI. Each Playwright version requires its corresponding browser binaries ([1.64.0](https://github.com/microsoft/playwright/releases/tag/v1.64.0), [1.63.0](https://github.com/microsoft/playwright/releases/tag/v1.63.0), [1.62.0](https://github.com/microsoft/playwright/releases/tag/v1.62.0), [browser installation](https://playwright.dev/docs/browsers)).
- **tsdown 0.23:** Its migration guide says to build once on 0.22.14 and resolve deprecation warnings. Among changes, `resolveDepSubpath` now defaults to false, obsolete compatibility options are removed, and Node 25 is unsupported. The project uses NodeNext resolution and does not appear to use the named removed options, but `src/diagrams.ts` resolves `pele/global` at runtime: verify the built and globally installed CLI can still resolve that subpath and render Mermaid. Do not assume a config rewrite is necessary merely because other options changed ([tsdown 0.23.0 migration guide](https://github.com/rolldown/tsdown/releases/tag/v0.23.0)).
- **TypeScript and Node types:** TypeScript 7.0.2 is already in use; the stable compiler is the native port, with defaults including `types: []` and a changed `rootDir`. This project's `tsconfig.json` already explicitly sets `types: ["node"]` and `noEmit: true`. Update `@types/node` deliberately to the 26 line and typecheck all source, scripts and tests; its npm `ts7.0` tag points to 26.6.6. Type definitions do not provide runtime APIs, and 26 types may permit APIs unavailable in Node 24 if 24 support is retained. The npm metadata for tsdown 0.23.4 allows TypeScript `^5 || ^6 || ^7`; that peer range is not proof the entire build works ([TypeScript 7 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), [Node types metadata](https://registry.npmjs.org/%40types%2Fnode), [tsdown metadata](https://registry.npmjs.org/tsdown)).
- **Oxc tooling:** `oxlint@1.90.0` requires peer `oxlint-tsgolint >=7.0.2005`; update them together, then rerun the project's type-aware lint with `--deny-warnings`. `oxfmt` crosses multiple pre-1.0 releases and formatting can change; run the check and review any proposed formatting diff. No specific repository failure is established by the version metadata ([oxlint metadata](https://registry.npmjs.org/oxlint), [Oxc releases](https://github.com/oxc-project/oxc/releases)).

## Migration outcome

- The project now targets Node.js 26.13.0 and pnpm 12.16.1. The pnpm 12 lockfile has two YAML documents; compatibility with GitHub's dependency scanning remains unverified.
- The user chose the newest releases that had passed the 24-hour age threshold: `@types/node` 26.6.5 and `tsdown` 0.23.3. pnpm's automatically added exceptions for their newer versions were removed, preserving the existing policy configuration.
- The transitive `source-map-js` dependency was updated to 1.2.2, resolving the high-severity advisory reported by `pnpm audit` at the time of the upgrade.
- A clean frozen install, validation, automated tests, and an isolated pnpm 12 global installation with a Mermaid PDF succeeded on macOS. A separately packed tarball was also installed globally in an isolated profile and converted the Mermaid fixture successfully. Windows, Linux, and GitHub's dependency scanning have not been verified.
- The existing global installer still sets `minimum-release-age=0` for its global add; this pre-existing bypass was not changed by the migration.
